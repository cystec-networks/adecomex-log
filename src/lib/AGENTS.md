# Email intake pipeline rules
- Order covers read saved order/products under RLS through `pdf-portada-orden`; use current operational values and frozen quote references, paginate vector rows without omissions, and download a prepared Blob on a separate click for mobile activation.
- Expediente create/update duplicate diagnostics use `expediente-duplicados` to decode the rejected constraint/value; reference lookups use the authenticated client under RLS and never change numbering or database uniqueness guards.
- Order operational fields are initialized from cot_* snapshots by an INSERT-only trigger; `orden-operativa` keeps later saves independent and downstream expediente conversion uses operational values rather than quotation history.
- BL destination costs use `bl-collect-charges` to sum explicit USD amounts from the quoted Collect section, not rates or repeated totals; combine BL and invoice sources once before draft application so rescans preserve manual edits.
- `tipo-carga-documento` validates OCR evidence for inferred FCL; explicit cargo declarations retain priority and ambiguous container lists remain medium-confidence across manual and email OCR.
- `cliente-documento` matches catalog client base names without legal suffixes; exact unique names autofill, probable equivalents require selection, preserving manual choices and ambiguous identities.
- Commercial invoices use `factura-comercial-cif` for explicit CIF Cost/FOB precedence; `agregarProductosFactura` consolidates draft products with documentary identity and matching tax rules. Documentary product IDs are not DGA codes and remain draft-only, preventing incorrect customs bases and unsupported writes.
- Document countries use `pais-documento` with explicit US/territory evidence and exact catalog resolution, shared by OCR and manual/email forms, because substring-first matching can select an unrelated island entry.
- Sales invoice transport references stay separate from fiscal descriptions. `factura-lineas-destino` scopes container matching by expediente after TR-first matching; mixed invoices persist exclusive destinations on fiscal lines through `guardar_lineas_ecf`, preserving line IDs. Transport membership remains in `transporte_facturas_ecf` (several per invoice); amounts come from `facturas_ecf_asignaciones` when present, else assigned lines, else full totals for legacy invoices. Customs costs use assigned pre-tax bases, while fiscal/CxC totals remain whole; manual lists retain drafts until save.

- `gastos-agrupados` groups pending fee rows by expediente ID and provider only for consolidated Finance; selection retains individual expense IDs so payments and exports stay unchanged.
- `honorarios-pago` supplies selection and payload rules for both payment directions; reversal clears the date and writes are guarded by the previous state to preserve concurrent corrections.

- Email service requests land in `solicitudes_correo` (staging), never as `expedientes` rows; "Confirmar y activar" opens the normal new-expediente form prefilled (`?correo=`), so drafts never reach reports/finance and numbering stays identical to manual creation.
- Commercial email invoices and manual scans share `ai-ocr.server` extraction and `factura-expediente-escaneo` enrichment; persist merchandise through the normal new-expediente form, reusing stored OCR lines and reading legacy drafts from their invoice file so both paths remain equivalent.
- Seguimiento SIGA uses pure `seguimiento-siga.ts` (fixed-rule reading: portal PDFs by positioned cells via `textoEItemsPdf`, then line text, AI only last; matching BL via `blParaEmparejar` (hijo, or document BL only when Tipo de BL is Simple) plus client/port validation, blank-only decision, informative-only fields never written) and `seguimiento-siga-evaluar.ts` with an injected DB client so manual (RLS) and email (service) paths share one evaluation; writes go only through invoker RPC `aplicar_seguimiento_siga` (blank-only guards, `siga_auto` provenance, process history keyed by process + request number and updated in place, processing date `fecha` with optional `fecha_creacion`, Auditoría; Checklist dispatch milestones go through security-definer `aplicar_hito_despacho_siga` and use the Despacho processing date) and the reading (or a `sin_lectura` reason, never silent) lives in `documentos.lectura_siga` keyed to its file so replacements ask to read again.
- Expediente «Completado» lives in `expediente-cierre.ts` (display/batch preview, timeline, lock payload) mirrored by SQL `pendientes_cierre_desde_hechos` over `hechos_cierre_expedientes`; change both together (parity is checked against real rows). Closing balances come from the expediente's e-CF invoices with `cxc_pagos` (same balance as Cuentas por Cobrar); pre-cutoff balances are amber warnings that never block, and completing never touches invoices/payments, so Completados stay in collections and mora alerts. The closing snapshot is built from a fresh read at confirmation. Entering/leaving Completado only through `completar_expediente`/`reabrir_expediente`/lote RPCs (session flag `app.cierre_expediente`), and a trigger blocks changing already-saved critical values while blank fills stay allowed so automatic readers never fail.
- Storage object names must never contain `#`: the API truncates the key at that character when the path is sent unencoded (the upload still answers 200) and rejects it outright when encoded, so every upload key has to pass its file name through `nombreArchivoStorage` (before any other sanitizing) and `documentos.storage_path` must always equal the key that actually exists — a mismatch leaves the document unopenable while the row looks healthy.
- Document «Eliminar» never hard-deletes: `documento_enviar_papelera` snapshots the row, versions and endorsement/SIGA links into `documentos_papelera` and keeps the file, so every reader of `documentos` ignores trashed rows without filters; restore (30 days) re-inserts the same id preserving stamps, and only admin purge removes files. «Cambiar tipo» goes through `documento_cambiar_tipo` (same file, no version, reads reset) and re-reads in simulation before applying selected blank fields.
- BL/AWB and commercial-invoice autocompletion of an existing expediente uses pure `autocompletar-operativo` (blank-only decision, alert vs grey-note split) and `autocompletar-operativo-evaluar` (injected DB client). Automatic reading on upload/email runs only for expedientes created since `AUTOCOMPLETADO_OPERATIVO_DESDE`; older ones are read one at a time from the document's «Leer ahora» (`leerDocumentoOperativo`, economy model, one read per file version). Every reading is stored as `lectura_operativa` «pendiente» and only the «Datos detectados» preview writes, through the audited RPC; the batch functions stay dormant without UI. Imported-document dates go through `fecha-documento` (printed literal, always day/month/year) so OCR can never swap day and month.
- Applying detected BL/invoice data (`aplicar_autocompletado_operativo`) recalculates `total_cif` whenever a CIF component is filled (undo recomputes too), and the open expediente form receives the applied fields via `EVENTO_AUTOCOMPLETADO_APLICADO` + `camposAplicadosParaFormulario`, filling only blank/untouched fields so a later global save never rewinds them nor drops unsaved edits.
- Regenerable packages (Rectificación Técnica, Envío Factura Cliente) keep only the latest PDF: `reemplazarPaquete` returns the replaced paths, the UPDATE uses `origen_cambio='regenerado'` (audited, no version) and `retirarArchivosPaqueteAnterior` deletes a path only when `paquete_archivo_retirable` confirms it is that Expediente's package and unreferenced, because packages are rebuildable from their sources.
- Email intake rules (webhook, retries, attachments, confirmation queue, combined PDFs, AI pauses, quote client choice) live in `src/components/correos/AGENTS.md`; DUA and DGA receipt reading rules live in `src/components/AGENTS.md`.
