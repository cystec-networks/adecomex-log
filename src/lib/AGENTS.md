# Email intake pipeline rules
- Order covers read saved order/products under RLS through `pdf-portada-orden`; use current operational values and frozen quote references, paginate vector rows without omissions, and download a prepared Blob on a separate click for mobile activation.
- Expediente create/update duplicate diagnostics use `expediente-duplicados` to decode the rejected constraint/value; reference lookups use the authenticated client under RLS and never change numbering or database uniqueness guards.
- Order operational fields are initialized from cot_* snapshots by an INSERT-only trigger; `orden-operativa` keeps later saves independent and downstream expediente conversion uses operational values rather than quotation history.
- BL destination costs use `bl-collect-charges` to sum explicit USD amounts from the quoted Collect section, not rates or repeated totals; combine BL and invoice sources once before draft application so rescans preserve manual edits.
- `tipo-carga-documento` validates OCR evidence for inferred FCL; explicit cargo declarations retain priority and ambiguous container lists remain medium-confidence across manual and email OCR.
- `cliente-documento` matches catalog client base names without legal suffixes; exact unique names autofill, probable equivalents require selection, preserving manual choices and ambiguous identities.
- Commercial invoices use `factura-comercial-cif` for explicit CIF Cost/FOB precedence; `agregarProductosFactura` consolidates draft products with documentary identity and matching tax rules. Documentary product IDs are not DGA codes and remain draft-only, preventing incorrect customs bases and unsupported writes.
- Document countries use `pais-documento` with explicit US/territory evidence and exact catalog resolution, shared by OCR and manual/email forms, because substring-first matching can select an unrelated island entry.
- Sales invoice transport references stay separate from fiscal descriptions. `factura-lineas-destino` scopes container matching by expediente after TR-first matching; mixed invoices persist exclusive destinations on fiscal lines through `guardar_lineas_ecf`, preserving line IDs. Transport membership remains in `transporte_facturas_ecf`; triggers and UI sum assigned lines for split invoices and full totals for legacy invoices. Customs costs use assigned pre-tax bases, while fiscal/CxC totals remain whole; manual lists retain drafts until save.

- `gastos-agrupados` groups pending fee rows by expediente ID and provider only for consolidated Finance; selection retains individual expense IDs so payments and exports stay unchanged.
- `honorarios-pago` supplies selection and payload rules for both payment directions; reversal clears the date and writes are guarded by the previous state to preserve concurrent corrections.

- Email service requests land in `solicitudes_correo` (staging), never as `expedientes` rows; "Confirmar y activar" opens the normal new-expediente form prefilled (`?correo=`), so drafts never reach reports/finance and numbering stays identical to manual creation.
- Email retries run OCR before the service-only invoker RPC `guardar_solicitud_correo_pendiente`, which serializes per sender and merges only matching pending drafts and attachment data; the legacy RPC delegates to it so deployed older callers also cannot duplicate pendings.
- Email attachments are read with the shared `PROMPT_DOCUMENTO_IMPORTACION`, stored under `documentos/correo/<uuid>/` and listed with extracted data in `solicitudes_correo.adjuntos`; `documentos` rows are only created on confirm, because drafts have no expediente. Normalize sender aliases/MIME via `correo-adjuntos` and expose rejected/failed attachments instead of dropping them silently. Field priority (attachment > subject > body) lives in `fusionarAdjuntos`/`fusionarAsunto`; confirmation must check document write errors before marking the request confirmed.
- Commercial email invoices and manual scans share `ai-ocr.server` extraction and `factura-expediente-escaneo` enrichment; persist merchandise through the normal new-expediente form, reusing stored OCR lines and reading legacy drafts from their invoice file so both paths remain equivalent.
- Confirmation queue responses are never cached; shared queue reads require pending status and no delivery timestamp, acknowledgements read back persistence, and a database trigger keeps sent status/timestamp immutable so delivered IDs cannot re-enter the queue. Log only queue IDs and status timestamps for diagnosis.
- Multi-document email PDFs (>4 pages or gateway timeout) are queued in `correo_documentos_combinados`, woken by a DB insert trigger (pg_net, no polling) calling `/api/public/documentos-combinados`; `correo-documento-combinado.server.ts` splits by page headers and files segments into the draft or expediente, keeping the original as backup, so the webhook never blocks.
- Operations KPI card order is a per-user `preferencias_usuario` row normalized by `panel-kpi-orden` (unknown ids dropped, new cards appended), so adding a KPI never hides it from users with a saved order.
- Atención requerida block layout is a per-user `preferencias_usuario` row of two complete columns normalized by `panel-alertas-disposicion`; no row means automatic balancing, and empty blocks keep their slot so they reappear where the user placed them.
- Transport list profit/CxC discount use `transporte-ganancia`, the same breakdown as the payment-request receipt; each request belongs to its own transporte_id (fallback: earliest transport referencing it), voided requests excluded, so list totals and receipts never diverge. List Flete is the receipt's gross amount to bill and Total Pagado its computed net; neither reads the editable/splittable `flete_monto`. Per-user card/column orders use generic `orden-preferencia` normalization so new ids append.
- Transport dashboard metrics come from `transportes-dashboard` over the same `transporte-ganancia` breakdown as the list (income = gross amount to bill, margin = profit); containers prefer the explicit billing count, else unique ISO container codes; billed = facturado state or any linked e-CF, one state per trip; deltas compare the equivalent previous week/month/year and return null without a base. Pending collection = income × (1 − collected fraction), where the fraction comes from linked e-CF invoices' `cxc_pagos` (same balance as Cuentas por Cobrar, weighted by the trip's assigned share) because invoices include ITBIS/mixed services and the manual transport `pago_estado` is rarely updated; manual «pagado» counts as fully collected.
- Transport dashboard KPI, state-card and page-block (Estados, Contenedores, Rentabilidad) orders are separate per-user `preferencias_usuario` rows normalized through `orden-preferencia` with ids from `transportes-dashboard-disposicion`; block ids added later that were always on top use `alInicio` so older saved orders keep them first; state chart/legend follow the card order so the view stays consistent.
- Imports dashboard periods and comparisons come from `importaciones-dashboard`: imports count on their real arrival date (`fecha_llegada_real`) and those without it are reported apart (in transit vs past-arrival state missing the date), while billed/expenses use each invoice/expense date so financial totals never move when arrival is confirmed; an in-progress week/month/year compares against the same elapsed span of the previous one, deltas return null without a base, and KPI and page-block orders are separate per-user `orden-preferencia` rows.
- The internal assistant (`asistente-virtual.server.ts` via `/api/asistente`) verifies a staff bearer token, forwards only sanitized text turns from `historialParaModelo`, has no tools, and its only database read is `novedades_comercio_exterior` under the user's RLS (recent + keyword matches injected as data), so it can never expose or invent business data; FAQ buttons come from the admin-editable `asistente_preguntas_frecuentes` table and history lives only in tab sessionStorage.
- Trade news come from admin-managed `fuentes_novedades`, reviewed by `novedades-comercio.server` (daily pg_cron → `/api/public/novedades/revisar` gated by a DB-only private token, or admin server fn): deterministic RSS/HTML link extraction, dedupe by SQL `novedad_url_clave` (mirrored by `claveUrl`) across saved and discarded rows, bounded sources/items with one AI call per source, single-flight lease and persisted pause on AI credit/access errors.
- Assistant read-aloud uses only the browser's native SpeechSynthesis through `use-lectura-voz` and pure `asistente-voz` helpers (Spanish voice choice, Markdown stripping, short chunks for Chrome's long-utterance cutoff); voices are awaited via `voiceschanged`, speak runs inside the click when possible, a pause follows any cancel, failures retry once with the system voice and then show a toast; one reading at a time, cancelled on new questions, minimize/close and unmount, so no external voice service or AI credits are involved.
