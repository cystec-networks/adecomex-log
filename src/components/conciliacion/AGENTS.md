# Bank reconciliation rules
- Exact-suggestion TF assignment runs only through `private.tf_para_entradas` (preview and confirm share it); hand-typed prior-register TFs are validated there, reserved before automatic numbers, never move the sequence and set `tf_excel` instead of `tf_retroactivo`, so preview and commit cannot diverge.
- Auto-reconciliation (post-import and "pending existing") goes only through `ejecutarConciliacionAutomatica` → `planConciliacionAutomatica` (pure, tested; actions conciliar/crear/no_aplica/comision, review reasons, excluded entries) → `conciliar_automatico_importacion`, which revalidates every item in its own savepoint and records an undoable `banco_lotes_automaticos` batch. Previews call it with `p_simular` (does everything, then rolls back via a caught custom SQLSTATE) and confirms pass `p_previsto`, so preview and commit share one code path and a changed result saves nothing; the TF sequence is setval'd once after the batch is accepted because setval is not transactional.
- Undoing an auto batch removes TFs it put on pre-existing entries (restoring the recorded previous numbers) and inserts them into `tf_sin_uso_notas` with `reutilizar`; every TF assignment path (`tf_para_entradas`, `crear_entrada_diario_desde_banco`, `previsualizar_tf`, the `tf_nuevo_numero()` column default) takes the lowest free reusable TF first, a trigger drops it from the list once used, and `siguiente_tf()` is max-based so a reused low number never rewinds the sequence.
- Bank reconciliation (debits only) uses `conciliacion-diario` for suggestions, account/beneficiary catalog summaries, batch selections (pre-Diario, commissions, retroactive groups), import dedupe (statement imports always show a `resumenImportacion` preview and recompute it on confirm, so nothing is inserted unseen) and balance checks, and writes only through locked RPCs (`conciliar_movimiento_diario`, `crear_entrada_diario_desde_banco`, `crear_entradas_diario_lote`, `marcar_no_aplica_lote`/`deshacer_lote_no_aplica`, `conciliar_exactas_lote`/`deshacer_lote_conciliacion` (all-or-nothing batch of `sugerenciasExactas`: one single-entry exact suggestion per debit, entries offered to two debits excluded; `lote_conciliacion` is cleared by any undo so undoing a batch never touches a later reconciliation; rows without TF start unselected and optional TF assignment uses `previsualizar_tf_exactas` and the same `private.tf_para_entradas` on confirm (a single free TF noted on the trips only when the nearest saved lower and higher TFs exist and the debit date falls between their dates, because «N° Ref. Pago» is not the payment-number field and held wrong values; else next free; assigned rows get `tf_retroactivo`, shown in the Diario), aborting if it differs from the preview so nothing is consumed unseen, and assigned TFs survive undo; accounts with two beneficiaries (`cuentasConVariosBeneficiarios`) require a per-row choice that must match the entry, re-checked server-side, unless the account is registered as shared: `banco_cuentas_beneficiario.titulares` (≥2) makes any holder a verified match, and creating entries for it never assumes a holder — a per-movement choice is required in the UI and enforced by `crear_entrada_diario_desde_banco`), `deshacer_conciliacion_banco`, `marcar_movimiento_banco`); every batch shows a preview and runs only on confirmation. Links live in `banco_conciliaciones`; bank-created TFs take `siguiente_tf()` (previewed by `previsualizar_tf`) and are voided, never deleted; commissions with a same-reference payment are linked, never given a TF; unused TF gaps come from `vista_tf_sin_uso`; the Diario view joins non-trashed transports by `solicitud_pago_id`, one row per payment, so a trashed duplicate never shows or counts twice.
