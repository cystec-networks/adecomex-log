# Bank reconciliation rules
- Exact-suggestion TF assignment runs only through `private.tf_para_entradas` (preview and confirm share it); hand-typed prior-register TFs are validated there, reserved before automatic numbers, never move the sequence and set `tf_excel` instead of `tf_retroactivo`, so preview and commit cannot diverge.
- Auto-reconciliation (post-import and "pending existing") goes only through `ejecutarConciliacionAutomatica` → `planConciliacionAutomatica` (pure, tested; actions conciliar/crear/no_aplica/comision, review reasons, excluded entries) → `conciliar_automatico_importacion`, which revalidates every item in its own savepoint and records an undoable `banco_lotes_automaticos` batch. Previews call it with `p_simular` (does everything, then rolls back via a caught custom SQLSTATE) and confirms pass `p_previsto`, so preview and commit share one code path and a changed result saves nothing; the TF sequence is setval'd once after the batch is accepted because setval is not transactional.
- Undoing an auto batch removes TFs it put on pre-existing entries (restoring the recorded previous numbers) and inserts them into `tf_sin_uso_notas` with `reutilizar`; every TF assignment path (`tf_para_entradas`, `crear_entrada_diario_desde_banco`, `previsualizar_tf`, the `tf_nuevo_numero()` column default) takes the lowest free reusable TF first, a trigger drops it from the list once used, and `siguiente_tf()` is max-based so a reused low number never rewinds the sequence.
